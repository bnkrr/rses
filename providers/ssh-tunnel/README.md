# SSH Tunnel Provider

The `ssh-tunnel` provider runs a persistent OpenSSH forwarding session under
rses. It supports local, remote, SOCKS, and Unix-socket forwarding, and
reconnects when `ssh` exits.

## Requirements

- Python 3 is required when rses loads the configuration.
- The system `ssh` client is required while the session runs.
- The configured SSH host alias and authentication must already work.

`rses init` installs this directory as `providers/ssh-tunnel/` beside the
generated `rses.yaml`. Provider code is executable code; only replace it with
code from a trusted source.

## Basic Example

This session forwards local port `3000` to port `3000` on `dev-box`:

```yaml
sessions:
  api-tunnel:
    backend: tmux
    provider: ssh-tunnel
    summary: 127.0.0.1:3000 -> dev-box:127.0.0.1:3000
    with:
      host: dev-box
      mode: local
      listen: 127.0.0.1:3000
      target: 127.0.0.1:3000
```

```bash
rses start api-tunnel
rses logs --follow api-tunnel
rses stop api-tunnel
```

Use `backend: tmux` when the SSH client and listening endpoint should run on
the local machine. Fields such as `depends_on`, `stop_dependencies`, `group`,
and `tags` are standard rses session fields documented in the
[rses README](https://github.com/bnkrr/rses#readme).

## How `with` Becomes `command`

The provider reads the values under `with`, validates them, and returns a
normal rses `command`. For example:

```yaml
with:
  host: dev-box
  mode: local
  listen: 127.0.0.1:3000
  target: 127.0.0.1:3000
```

The forwarding part becomes this SSH invocation:

```bash
ssh -N \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=15 \
  -o ServerAliveCountMax=3 \
  -o TCPKeepAlive=yes \
  -o BatchMode=yes \
  -L 127.0.0.1:3000:127.0.0.1:3000 \
  dev-box
```

The returned command has the following shape:

```yaml
command:
  argv:
    - sh
    - -c
    - <reconnect loop that runs the SSH command above>
```

The shell wrapper is generated by the provider and retries the SSH command
with backoff. Run `rses explain api-tunnel` to inspect the complete generated
command and wrapper before starting the session.

## Parameters

All provider parameters belong under `with`.

| Parameter | Required | Description |
| --- | --- | --- |
| `host` | Yes | Host or alias passed to the system `ssh` command. |
| `mode` | Yes | One of `local`, `local-socket`, `remote`, `remote-socket`, or `socks`. |
| `listen` | Yes | Listening TCP address or remote Unix-socket path, depending on `mode`. |
| `target` | Except for `socks` | Forwarding destination, interpreted according to `mode`. |
| `ssh_args` | No | Array of additional arguments inserted before the provider defaults. |

`ssh_args` is a list of individual argv values, not a shell command string:

```yaml
with:
  host: dev-box
  mode: local
  listen: 127.0.0.1:3000
  target: 127.0.0.1:3000
  ssh_args: ["-p", "2222", "-i", "/home/me/.ssh/dev_ed25519"]
```

These arguments configure the long-running tunnel. They are separate from
`runtime.ssh.extra_args`, which configures rses queries and operations for
`ssh-tmux` sessions.

## Forwarding Modes

### Local TCP forwarding

`local` produces `ssh -L LISTEN:TARGET`. `listen` is opened where this
provider session runs, and `target` is reached from the SSH server.

```yaml
with:
  host: dev-box
  mode: local
  listen: 127.0.0.1:3000
  target: 127.0.0.1:3000
```

### Local TCP to remote Unix socket

`local-socket` also uses `ssh -L`, but `target` must be an absolute Unix-socket
path on the SSH server.

```yaml
with:
  host: agent-box
  mode: local-socket
  listen: 127.0.0.1:35003
  target: /home/agent/.local/state/rses/codex-app-server.sock
```

### Remote TCP forwarding

`remote` produces `ssh -R LISTEN:TARGET`. `listen` is opened by the SSH
server, and `target` is reached from the machine running this provider.

```yaml
with:
  host: dev-box
  mode: remote
  listen: 127.0.0.1:18080
  target: 127.0.0.1:3000
```

Whether a non-loopback remote address can be exposed is controlled by the SSH
server configuration.

### Remote Unix socket forwarding

`remote-socket` uses `ssh -R`. `listen` must be an absolute Unix-socket path
on the SSH server, and `target` is reached from the machine running this
provider.

```yaml
with:
  host: dev-box
  mode: remote-socket
  listen: /tmp/local-api.sock
  target: 127.0.0.1:3000
```

### Local SOCKS proxy

`socks` produces `ssh -D LISTEN` and does not use `target`.

```yaml
with:
  host: dev-box
  mode: socks
  listen: 127.0.0.1:1080
```

## Runtime Behavior

The generated SSH command includes these defaults:

```text
-N
-o ExitOnForwardFailure=yes
-o ServerAliveInterval=15
-o ServerAliveCountMax=3
-o TCPKeepAlive=yes
-o BatchMode=yes
```

The provider keeps retrying after `ssh` exits. Short-lived failures back off
to at most 30 seconds between attempts; after a connection survives for at
least 60 seconds, the retry delay resets.

Tunnel output and SSH errors are written to the rses session log. Because
`BatchMode=yes` is enabled by default, interactive password prompts are not
suitable for these background sessions. Complete SSH or proxy authentication
in a terminal first, or configure non-interactive authentication.

Bind local listeners to `127.0.0.1` unless other machines intentionally need
access. rses manages the process lifecycle but does not replace SSH host,
server, key, or network security configuration.
